## 3. FIXED — tip change could capture money without crediting it

**Severity: P0.** `3208ea7`. Option (b) below was taken.

The retired attempt is now marked **`superseded`** instead of `canceled`:

- outside `creating|open|requires_action`, so the replacement attempt still reserves;
- not a terminal state `terminalWouldRegress` protects, so money on a still-live
  retired Intent settles normally;
- a genuine cancellation stays `canceled` and stays unsettleable.

No migration was needed — `superseded` is already in the applied
`CREATE TYPE "PaymentAttemptStatus"`, verified against the migration SQL and not
only against `schema.prisma`.

**Still open (option (a), latency not correctness):** the Stripe cancel runs
inside the advisory-lock interactive transaction — two Stripe round trips per
request against a 14s timeout. Moving it out changes the race between cancel and
reservation, so it was left alone.

The original analysis follows.

`netlify/lib/db/payment-authority-service.js` → `cancelActiveAttemptsForTipChange`

```js
try {
  await fetchImpl(`https://api.stripe.com/v1/payment_intents/${attempt.providerObjectId}/cancel`, …);
} catch (_) { /* best-effort cancel; attempt row still closed below */ }
await prisma.paymentAttempt.update({ where: { id: attempt.id }, data: { status: 'canceled' } });
```

Three problems compound:

1. **A second Stripe call now runs inside the advisory-lock interactive
   transaction** (`timeout: 14_000`), whose own comment says *"Stripe work
   inside the lock must stay short."* Cancel + create per request.
2. **The cancel is best-effort but the row is marked `canceled` regardless.**
   If Stripe never received the cancel, the PaymentIntent stays live while the
   local row says otherwise — an orphan.
3. **The webhook then refuses that money** (`payment-authority-service.js:743`):

```js
terminalWouldRegress = … || (attempt.status === 'canceled' && paymentIntent.status !== 'canceled')
```

**Failure path:** customer changes tip → cancel fails → customer pays the
Payment Element still mounted with the old client secret → Stripe captures →
webhook rejects → **money taken, invoice still shows due.**

### Options (not implemented)

- **(a)** Move the cancel outside the lock and make it idempotent/retryable;
  keep the row `canceled` only after Stripe confirms.
- **(b)** Let the webhook credit a PI whose attempt was cancelled *for tip
  change specifically* (needs a distinct status such as `superseded`, so a real
  cancellation still cannot settle).
- **(c)** Do not cancel at all; leave the old attempt open and rely on the
  amount mismatch to refuse it — the customer simply pays the current amount.

(b) is the smallest change that closes the money hole; (a) is the smallest that
reduces lock pressure. They are complementary.

## 4. Tip partition — verified sound

The design itself is right, and worth keeping.

| Property | Verdict | Evidence |
|---|---|---|
| Overpay | safe | settlement ledger writes `balanceCents`, not the PI total |
| Invoice inflation | safe | tip is `kind:'fee'`; `computeFinancialProjection` counts only `settlement`/`adjustment`/`refund` |
| `outstandingCreditCents` | safe | follows from the above |
| Duplicate tip credit | safe | unique `providerEventId = tip_${pi.id}` |
| Amount tampering | safe | `amount_received !== attempt.amountCents` guard preserved; plus `payment_tip_partition_mismatch` |
| Tip caps | safe | 40% of balance and $500, both applied whether the client sends `tipCents` or `tipPercent` |
| **Refund** | **gap** | `refundableCents = settledCents − refundedCents`, and `settledCents` excludes the tip — **a full refund cannot return the tip** |

The refund gap is a product decision, not a defect: many products do not refund
tips automatically. It is currently undocumented and unsurfaced in the UI.

## 5. Answers to the handoff's questions

1. **Tip partition safe?** Yes for overpay/credit/duplication. **No for refund** — see above.
2. **Idempotency / orphan PI?** `buildIdempotencyKey` includes `amountCents`, so a tip change mints a distinct key and no Stripe key collision occurs. The orphan risk is real and is item 3.
3. **Reuse of PaymentIntent — is "hide + Pay again" enough?** Not on its own; it depends on the cancel succeeding. See item 3.
4. **Receipt limited auth via sessionStorage?** Covers the lookup path. Not verified for magic-link/action-token deep links opened in a fresh browser with no `cd1_garage_*` keys — untested here.
5. **Create modal payload?** Not audited this pass.
6. **`Math.round(dollars * 100)`?** No exploitable edge found; the tip module clamps by two independent ceilings before the value is used.
7. **Cash/card on-site / reconcile / hosted-Checkout isolation regressions?** None found in the suite differential.
8. **Should tip reach the receipt and tech payout?** Not currently. Minimum contract without touching Stripe UI: expose `technicianTipCents` in the receipt projection as a separate line under the settled total, and leave `techPayoutAmount` alone until payout policy is decided.
